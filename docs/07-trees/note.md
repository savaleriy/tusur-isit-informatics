# Часть 1. Графы

Массив, список и хеш-таблица хранят элементы, у которых есть естественный порядок или ключ. Но многие задачи описывают не сами элементы, а **связи** между ними: города и дороги, людей и знакомства, страницы и ссылки, детали и зависимости при сборке. Для таких задач есть отдельный язык - графы.

**Граф** - это набор **вершин** и **рёбер**, которые соединяют пары вершин. Вершины изображают объекты, рёбра - связи. Формально граф задают парой $G = (V, E)$, где $V$ - множество вершин, а $E$ - множество рёбер. Число вершин обозначают $|V|$, число рёбер - $|E|$.

Граф на рисунке можно прочитать как карту: вершины - города, рёбра - дороги между ними.

![Граф: BFS обходит по слоям, DFS уходит вглубь](images/graph.svg#only-light)
![Граф: BFS обходит по слоям, DFS уходит вглубь](images/graph.dark.svg#only-dark)

Рёбра бывают **неориентированными** - дорога работает в обе стороны, - и **ориентированными**: стрелка показывает, что связь односторонняя, как подписка или ссылка на страницу. Если у ребра есть число - расстояние, стоимость, время, - граф называют **взвешенным**.

Ещё несколько слов, без которых не читается ни одна задача про графы:

- **путь** - последовательность вершин, где каждые две соседние соединены ребром;
- **цикл** - путь, который начинается и заканчивается в одной вершине;
- **связный граф** - из любой вершины можно дойти до любой другой;
- **степень вершины** - сколько рёбер из неё выходит.

Одна и та же задача может выглядеть по-разному. "Сколько дорог нужно построить, чтобы все города стали связаны?" - вопрос про рёбра. "Можно ли добраться из A в B?" - про путь. "Есть ли кольцевой маршрут?" - про цикл. Научившись видеть граф, вы получаете готовый набор алгоритмов для всех трёх.

## Как хранить граф

Две вершины и ребро между ними - это мало. Программе нужно быстро отвечать на вопрос "кто сосед этой вершины?", и от выбранного хранилища зависит скорость.

**Список смежности** хранит для каждой вершины список её соседей:

```python
graph = {
    "A": ["B", "C"],
    "B": ["A", "D", "E"],
    "C": ["A", "F"],
    "D": ["B"],
    "E": ["B", "F"],
    "F": ["C", "E"],
}
```

В неориентированном графе ребро записывается дважды: `B` есть в списке `A`, а `A` - в списке `B`. Память - $O(|V| + |E|)$, а соседи вершины читаются за $O(\deg v)$. Для разреженных графов, где рёбер ненамного больше, чем вершин, это лучший выбор.

**Матрица смежности** - таблица $|V| \times |V|$, где в ячейке `[i][j]` стоит 1, если ребро есть, и 0, если нет. Проверка "есть ли ребро" занимает $O(1)$, но память - $O(|V|^2)$: для миллиона вершин таблица не поместится ни в какую память. Матрица выгодна для плотных графов и когда рёбра проверяются постоянно.

| | Список смежности | Матрица смежности |
| - | - | - |
| Память | $O(V + E)$ | $O(V^2)$ |
| Соседи вершины | $O(\deg v)$ | $O(V)$ |
| Проверить ребро | $O(\deg v)$ | $O(1)$ |

## Обход графа

Обойти граф - значит побывать в каждой достижимой вершине ровно один раз. Здесь и появляются два классических способа: **поиск в ширину** (BFS) и **поиск в глубину** (DFS).

**BFS** идёт по слоям: сначала старт, потом все его соседи, потом соседи соседей. Для этого нужна **очередь**: вершины достаются из неё в том порядке, в котором были обнаружены. Множество `visited` не даёт положить одну вершину дважды - в графе, в отличие от дерева, в неё может вести несколько путей. Важно помечать вершину посещённой **при добавлении в очередь**: если делать это при извлечении, вершина с несколькими путями попадёт в очередь несколько раз.

```python
from collections import deque

def bfs(graph, start):
    visited = {start}
    queue = deque([start])
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append(neighbor)
    return order

bfs(graph, "A")   # ['A', 'B', 'C', 'D', 'E', 'F']
```

Порядок `A, B, C, D, E, F` - это слои: `A` на нулевом, `B` и `C` на первом, `D`, `E`, `F` на втором. Поэтому BFS в невзвешенном графе находит **кратчайший путь по числу рёбер**: вершина, до которой можно добраться за $k$ шагов, встретится не позже любого другого пути.

**DFS** уходит вглубь, пока есть куда, и только потом возвращается и пробует следующего соседа. Он пишется рекурсией почти так же, как обход дерева:

```python
def dfs(graph, node, visited=None):
    if visited is None:
        visited = set()
    visited.add(node)
    order = [node]
    for neighbor in graph[node]:
        if neighbor not in visited:
            order.extend(dfs(graph, neighbor, visited))
    return order

dfs(graph, "A")   # ['A', 'B', 'D', 'E', 'F', 'C']
```

Разница видна по порядку: BFS сначала обошёл всех соседей `A`, а DFS сразу ушёл по первой ветке `A -> B -> D`, затем вернулся и продолжил.

Оба обхода стоят $O(|V| + |E|)$: каждая вершина попадает в `visited` один раз, а списки соседей просматриваются по одному разу. Для обхода **всех** вершин несвязного графа обход запускают из каждой ещё не посещённой вершины - так получают компоненты связности.

Дерево - это связный граф без циклов, то есть граф, в котором нет ни одного лишнего ребра. Такие графы и станут главными героями следующей части.

# Часть 2. Деревья

**Дерево** - это связный граф, в котором нет циклов. Между любыми двумя его вершинами есть ровно один путь, а рёбер всегда на одно меньше, чем вершин: $|E| = |V| - 1$. Уберите из дерева любое ребро - и оно распадётся на две несвязные части.

Именно отсутствие циклов и лишних путей делает деревья удобными для хранения данных: положение узла определено однозначно. Если выбрать одну вершину **корнем** и направить рёбра от неё, получится иерархия "родитель - потомок".

Терминология, которую стоит запомнить с первого раза:

- **корень** - узел без родителя, с него всё начинается;
- **лист** - узел без потомков;
- **ребро** - связь между родителем и потомком;
- **высота** - число узлов на самом длинном пути от корня до листа;
- **поддерево** - узел вместе со всеми его потомками.

## Бинарное дерево

**Бинарное дерево** - дерево, где у каждого узла не более двух потомков: левого и правого. Дальше речь пойдёт в основном о бинарных деревьях: на них строятся и дерево поиска, и куча, и код Хаффмана.

Узел бинарного дерева хранит данные и две ссылки - на левого и правого потомка:

```python
class Node:
    def __init__(self, data, left=None, right=None):
        self.data = data
        self.left = left
        self.right = right
```

## Обходы дерева

Обойти дерево - значит посетить каждый узел ровно один раз. В дереве нет циклов, поэтому, в отличие от общего графа, множество посещённых вершин не нужно: от каждого узла вниз ведёт ровно один путь. Разница между способами обхода - в том, **в каком порядке** мы заходим в узел относительно его потомков.

Три классических обхода бинарного дерева:

- **прямой** (pre-order): узел, потом левое поддерево, потом правое;
- **центрированный** (in-order): левое поддерево, узел, правое поддерево;
- **обратный** (post-order): левое поддерево, правое поддерево, узел.

Каждый записывается рекурсией в три строки. Различие только в том, где стоит строка "посетить узел" - до, между или после двух рекурсивных вызовов.

Возьмём дерево, где корень 1, левый потомок 2, правый потомок 3. Прямой обход даст `[1, 2, 3]`, центрированный - `[2, 1, 3]`, обратный - `[2, 3, 1]`.

Центрированный обход мы будем использовать чаще всего: на дереве поиска он выдаёт значения по возрастанию.

# Часть 3. Деревья поиска

**Двоичное дерево поиска** (BST) - это бинарное дерево с одним дополнительным правилом: **всё, что в левом поддереве узла, меньше него, а всё, что в правом, - больше**. Это правило действует для каждого узла, а не только для корня.

![Двоичное дерево поиска](images/bst.svg#only-light)
![Двоичное дерево поиска](images/bst.dark.svg#only-dark)

Правило превращает поиск в спуск по дереву: начиная с корня, сравниваем искомое с текущим узлом и уходим влево или вправо. Каждый шаг отбрасывает целое поддерево - ровно как бинарный поиск в массиве.

Найдём число 7 на рисунке: 7 меньше 10 - идём влево к 5; 7 больше 5 - идём вправо; нашли. Два сравнения вместо перебора всех узлов.

А теперь поищем 8: 8 меньше 10 - влево к 5; 8 больше 5 - вправо к 7; 8 больше 7 - вправо, а там пусто. Значит, числа 8 в дереве нет, и мы выяснили это за три сравнения, ни разу не заглянув в правое поддерево корня.

## Скорость определяется высотой

Насколько быстр поиск? Столько шагов, сколько узлов на пути от корня до искомого, - то есть не больше **высоты** дерева.

Тут и кроется подвох. Сбалансированное дерево из $n$ узлов имеет высоту около $\log_2 n$, и поиск в нём - $O(\log n)$. Но если вставлять элементы уже отсортированными, дерево вырождается в цепочку: каждый новый узел уходит только вправо. Такое дерево имеет высоту $n$, и поиск в нём - $O(n)$, не лучше связного списка.

Поэтому оценка "BST ищет за $O(\log n)$" верна **в среднем**, для случайного порядка вставки, но не гарантирована. Как гарантировать - разберём дальше.

## Вставка, удаление, минимум

**Вставка** - это тот же спуск: доходим до пустого места и подвешиваем туда новый узел.

**Удаление** сложнее, у него три случая: лист просто убираем; узел с одним потомком заменяем этим потомком; узел с двумя потомками заменяем его **преемником** - самым левым узлом правого поддерева, который перенимает его место. Преемника легко найти: из правого потомка всё время идём влево, пока есть куда.

**Минимум** - самый левый узел дерева, **максимум** - самый правый: просто идём влево или вправо до упора.

Итак, BST быстр, пока дерево не перекосилось. Как не дать ему перекоситься?

## АВЛ-деревья и повороты

Ответ - следить за формой дерева и выравнивать его, когда одна сторона перерастает другую. **АВЛ-дерево** (по фамилиям Адельсона-Вельского и Ландиса) хранит в каждом узле **коэффициент балансировки** - разность высот правого и левого поддерева - и требует, чтобы он всегда был в пределах от $-1$ до $1$.

Как только вставка выводит коэффициент за эти пределы, дерево **поворачивает** поддерево, чтобы восстановить баланс.

![Поворот АВЛ-дерева](images/rotation.svg#only-light)
![Поворот АВЛ-дерева](images/rotation.dark.svg#only-dark)

На рисунке - **левый поворот**: узел A был корнем, а правый потомок B перевешивал. После поворота B становится корнем, а A - его левым потомком. Порядок значений не меняется (мы просто переподвесили ветви), но высота сокращается.

Повороты бывают левыми и правыми, одиночными и двойными - разбирать их все здесь мы не будем. Важно понимать главное: **АВЛ-дерево гарантирует высоту $O(\log n)$**, а значит, поиск и вставку за $O(\log n)$ всегда, а не в среднем. Реализовывать АВЛ-дерево вручную вам вряд ли придётся - готовые сбалансированные деревья встроены в стандартные библиотеки, - но знать, почему они быстрые, полезно.

# Часть 4. Двоичная куча

Есть задача, для которой полное дерево поиска - избыточность: нужно только **мгновенно доставать минимальный элемент**. Например, очередь с приоритетом.

**Двоичная куча** решает её. Это бинарное дерево с одним правилом: **каждый узел не больше своих потомков**. Минимум, таким образом, всегда на вершине - достать его можно за $O(1)$.

![Двоичная куча](images/heap.svg#only-light)
![Двоичная куча](images/heap.dark.svg#only-dark)

Кучу удобно хранить не деревом, а **массивом**: корень в ячейке 0, потомки узла в ячейке $i$ - в ячейках $2i+1$ и $2i+2$. Тогда "просеять" новый элемент вверх или вниз - это обмены в массиве, и вставка с удалением минимума стоят $O(\log n)$.

Куча - ровно то, что стоит за очередью с приоритетом: операционная система держит процессы в куче, чтобы в любой момент достать самый приоритетный.

# Часть 5. Декартово дерево

BST быстр, пока высота мала, а АВЛ-дерево обеспечивает это поворотами и хранением коэффициента баланса. Есть способ проще: добавить к ключу случайность.

**Декартово дерево** (treap, от tree и heap) - это бинарное дерево, в каждом узле которого лежат **ключ** и **приоритет**. По ключам оно является деревом поиска, а по приоритетам - кучей: приоритет родителя больше приоритетов потомков. Ключи упорядочены, приоритеты случайны и не зависят от ключей.

Случайность и держит дерево в форме. Если бы все приоритеты были одинаковы, получился бы обычный BST, который мог бы выродиться в цепочку. Но при случайных приоритетах форма дерева распределена так же, как при случайной вставке ключей: даже отсортированный вход перемешивается приоритетами. Поэтому ожидаемая высота - $O(\log n)$, хотя гарантии, как у АВЛ-дерева, нет.

![Декартово дерево: ключи упорядочены, приоритеты образуют кучу](images/treap.svg#only-light)
![Декартово дерево: ключи упорядочены, приоритеты образуют кучу](images/treap.dark.svg#only-dark)

Все операции строятся на двух примитивах.

**`split(root, key)`** разрезает дерево на два: в первом ключи меньше `key`, во втором - больше или равны. Спуск идёт по ключу, как в BST, и переподвешивает ветви, но не меняет порядок ключей.

**`merge(left, right)`** склеивает два дерева при условии, что все ключи `left` меньше всех ключей `right`. Корнем становится узел с большим приоритетом: он и должен быть выше по свойству кучи. Второе дерево подвешивается к нему рекурсивно.

```python
import random


class Node:
    def __init__(self, key, priority=None):
        self.key = key
        self.priority = random.random() if priority is None else priority
        self.left = None
        self.right = None


def split(root, key):
    """Вернуть (ключи < key, ключи >= key)."""
    if root is None:
        return None, None
    if root.key < key:
        left, right = split(root.right, key)
        root.right = left
        return root, right
    left, right = split(root.left, key)
    root.left = right
    return left, root


def merge(left, right):
    """Все ключи left меньше всех ключей right."""
    if left is None:
        return right
    if right is None:
        return left
    if left.priority > right.priority:
        left.right = merge(left.right, right)
        return left
    right.left = merge(left, right.left)
    return right


def contains(root, key):
    while root is not None:
        if key == root.key:
            return True
        root = root.left if key < root.key else root.right
    return False


def insert(root, key):
    if contains(root, key):
        return root                 # повторный ключ не добавляем
    left, right = split(root, key)
    return merge(merge(left, Node(key)), right)


def delete(root, key):
    if root is None:
        return None
    if key == root.key:
        return merge(root.left, root.right)
    if key < root.key:
        root.left = delete(root.left, key)
    else:
        root.right = delete(root.right, key)
    return root


def inorder(root):
    if root is None:
        return []
    return inorder(root.left) + [root.key] + inorder(root.right)
```

Разберём, почему это работает.

- `split` идёт по одному пути от корня. Если ключ узла меньше `key`, узел и его левое поддерево точно попадают в левую часть, а правое поддерево ещё нужно разрезать. Если ключ не меньше, всё наоборот. Высота пути - высота дерева, поэтому `split` стоит $O(h)$.
- `merge` выбирает корнем узел с большим приоритетом и рекурсивно присоединяет к нему второе дерево. Порядок ключей не нарушается: все ключи левого дерева по-прежнему меньше всех ключей правого.
- `insert` разрезает дерево по ключу, вставляет новый узел между частями и склеивает обратно. `delete` находит узел и склеивает его левое и правое поддеревья - оба уже являются корректными treap.
- `contains` и `inorder` - обычные операции BST: спуск по ключу и центрированный обход.

| Операция | Время |
| - | - |
| `split`, `merge` | $O(h)$ |
| `insert`, `contains`, `delete` | $O(h)$ |
| `inorder` | $O(n)$ |
| Память | $O(n)$ |

В среднем $h = O(\log n)$, в худшем случае - $O(n)$, если случайные приоритеты случайно выстроились в неудачном порядке. Вероятность этого мала, поэтому treap проще АВЛ-дерева: не нужно хранить баланс и разбирать четыре случая поворотов. Плата - случайность: приоритеты должны быть независимы от ключей и действительно случайны.

```python
root = None
for key in (5, 2, 8, 1, 9, 3):
    root = insert(root, key)

contains(root, 3)   # True
contains(root, 4)   # False
inorder(root)       # [1, 2, 3, 5, 8, 9]
root = delete(root, 2)
inorder(root)       # [1, 3, 5, 8, 9]
```

# Часть 6. Деревья отрезков

Ещё одна задача, где массив недостаточно быстр: есть массив чисел, нужно отвечать на запросы "сумма на отрезке" и менять отдельные элементы. Префиксные суммы дают ответ за $O(1)$, но обновление элемента требует пересчитать весь хвост - $O(n)$. Нужна структура, где обе операции логарифмические.

**Дерево отрезков** - бинарное дерево над отрезками массива. Корень отвечает за весь массив, его дети - за левую и правую половины, листья - за отдельные элементы. В каждом узле хранится свёртка своего отрезка: для суммы - сумма, для минимума - минимум.

![Дерево отрезков: запрос от 1 до 4 складывает выделенные узлы](images/segment-tree.svg#only-light)
![Дерево отрезков: запрос от 1 до 4 складывает выделенные узлы](images/segment-tree.dark.svg#only-dark)

Запрос устроен так. Если отрезок узла целиком лежит внутри запроса, берём готовое значение из узла. Если он не пересекается с запросом, возвращаем нейтральный элемент (для суммы - 0). Иначе запрос делится между детьми, а их ответы объединяются.

Обновление - спуск к листу. Меняем значение в листе и на обратном пути пересчитываем суммы во всех предках.

```python
class SegmentTree:
    def __init__(self, values):
        self.n = len(values)
        self.tree = [0] * (4 * self.n)
        if self.n:
            self._build(1, 0, self.n, values)

    def _build(self, node, left, right, values):
        if right - left == 1:
            self.tree[node] = values[left]
            return
        mid = (left + right) // 2
        self._build(2 * node, left, mid, values)
        self._build(2 * node + 1, mid, right, values)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    def update(self, index, value):
        self._update(1, 0, self.n, index, value)

    def _update(self, node, left, right, index, value):
        if right - left == 1:
            self.tree[node] = value
            return
        mid = (left + right) // 2
        if index < mid:
            self._update(2 * node, left, mid, index, value)
        else:
            self._update(2 * node + 1, mid, right, index, value)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    def query(self, ql, qr):
        """Сумма на полуинтервале [ql, qr)."""
        return self._query(1, 0, self.n, ql, qr)

    def _query(self, node, left, right, ql, qr):
        if qr <= left or right <= ql:
            return 0
        if ql <= left and right <= qr:
            return self.tree[node]
        mid = (left + right) // 2
        return (self._query(2 * node, left, mid, ql, qr)
                + self._query(2 * node + 1, mid, right, ql, qr))
```

Разберём детали.

- Дерево хранится в массиве `tree` длиной $4n$: для узла с номером `node` дети лежат в `2 * node` и `2 * node + 1`. Номер 0 не используется, корень - узел 1. Четвёрки хватает с запасом на любую форму дерева.
- Отрезок задаётся полуинтервалом `[left, right)`. Лист - это `right - left == 1`, один элемент массива.
- `query(ql, qr)` тоже работает с полуинтервалом: `query(1, 4)` суммирует элементы с индексами 1, 2 и 3, не включая 4.
- Нейтральный элемент зависит от операции: для суммы это 0, для минимума - бесконечность, для произведения - 1. Главное, чтобы `x + нейтральный = x`.
- Дерево отрезков хранит не только суммы: в узле может лежать минимум, максимум, НОД или другая ассоциативная операция. Меняется только способ объединения ответов детей.

| Операция | Время |
| - | - |
| Построение | $O(n)$ |
| `query` | $O(\log n)$ |
| `update` | $O(\log n)$ |
| Память | $O(n)$ |

```python
st = SegmentTree([2, 5, 1, 4, 3])
st.query(1, 4)   # 10: 5 + 1 + 4
st.update(2, 7)
st.query(1, 4)   # 16: 5 + 7 + 4
st.query(0, 5)   # 21
```

Префиксные суммы выигрывают, если массив не меняется: они проще и отвечают за $O(1)$. Дерево отрезков нужно тогда, когда запросы и обновления чередуются: оно не даёт ни одной операции за $O(1)$, зато не позволяет ни одной вырасти до $O(n)$.

# Часть 7. Сжатие данных

Деревья - не только про скорость поиска. На них построен один из самых известных алгоритмов сжатия - **алгоритм Хаффмана**.

## Почему текст можно сжать

Сохраним слово "tilt" в файл. В кодировке, где каждый символ занимает один байт, файл весит 4 байта - по байту на букву.

Но задумаемся: нам нужно закодировать всего три разных буквы - `t`, `i`, `l`. Три символа можно различить и двумя битами, а не восемью. Уже экономия в четыре раза.

Однако Хаффман идёт дальше. Он подмечает, что буквы встречаются **не одинаково часто**: в "tilt" буква `t` встречается дважды, а `i` и `l` - по разу. Значит, частой букве стоит дать код покороче, а редким - подлиннее.

## Дерево Хаффмана

Строим дерево снизу вверх:

1. Каждой букве заводим узел с её частотой: `t` весит 2, `i` и `l` - по 1.
2. Берём два самых лёгких узла - `i` и `l` - и соединяем их общим родителем весом $1 + 1 = 2$.
3. Остаются два узла весом 2: буква `t` и наш родитель. Соединяем их корнем весом 4.
4. Левое ребро помечаем нулём, правое - единицей.

![Дерево Хаффмана для слова tilt](images/huffman.svg#only-light)
![Дерево Хаффмана для слова tilt](images/huffman.dark.svg#only-dark)

Код буквы - это путь от корня до её листа: `t` - это `0`, `i` - `10`, `l` - `11`.

Теперь закодируем слово: `t i l t` превращается в `0 10 11 0`, то есть в `010110` - шесть бит против тридцати двух в исходной записи. Буква `t`, самая частая, получила самый короткий код.

## Префиксные коды

Главное свойство кодов Хаффмана - **префиксность**: ни один код не является началом другого. В нашем примере `0`, `10` и `11` не перекрываются: прочитав `0`, мы точно знаем, что это `t`, а не начало `i` или `l`.

Благодаря префиксности декодирование однозначно: идём по битам, накапливая код, пока он не совпадёт с кодом какой-то буквы, - и выдаём её. Никаких разделителей между кодами не нужно.

Собственно, именно поэтому коды Хаффмана называют **оптимальным префиксным кодом**: среди всех префиксных кодов этот даёт самое короткое сообщение. Для текста, где частоты букв сильно различаются, сжатие оказывается заметным.

### 📝 Задача 5. Коды Хаффмана

> **Файл:** `huffman.py` | **Функция:** `huffman_codes(text)`

Постройте дерево Хаффмана для текста и верните словарь "буква - код". Код - это строка из нулей и единиц.

```python
huffman_codes("tilt")
# {'t': '0', 'i': '10', 'l': '11'}  (или с зеркальным 0/1)
```

Конкретные коды могут отличаться от примера: при равных частотах неважно, какой узел окажется слева, а какой справа. Важно, что код **префиксный** и что частая буква получает код не длиннее редкой.

Подсказка: понадобится приоритетная очередь, чтобы каждый раз доставать два самых лёгких узла. В [Python-конспекте](python.md) показан модуль `heapq`.

> **Проверьте себя:** почему алгоритм Хаффмана называют жадным? На каждом шаге он соединяет два самых лёгких узла - и при этом получает глобально оптимальный код. Не все жадные алгоритмы так удачливы, но этому повезло.

## B-деревья: деревья на диске

Напоследок - структура, которую вы вряд ли будете писать руками, но которая стоит за каждой базой данных.

Данные на жёстком диске читаются большими блоками, и каждый поход к диску дорог. **B-дерево** хранит в одном узле сразу много ключей и много указателей, поэтому за одно чтение с диска мы забираем больше данных. Читать с диска приходится реже - и база работает быстрее.

B-дерево сохраняет главное свойство дерева поиска: значения в поддеревьях левого указателя меньше ключа, правого - больше. Просто каждый узел - это целая таблица ключей, а не один ключ.

Это хорошая иллюстрация эпиграфа: пока данные помещаются в память, обычного BST хватает. Переходить на B-деревья стоит тогда, когда данные уходят на диск, - не раньше.
