# Часть 1. Тип данных и АТД

Мы различаем крепёж - винты, гайки и гвозди - по операциям, которые с ними выполняют: отверткой, гаечным ключом или молотком. С данными то же самое: **тип данных** определяется набором операций, которые с ним можно делать.

Строка допускает преобразование в верхний регистр и добавление символов. Логическое значение - операции `AND`, `OR`, `NOT`. Число - сложение, деление, вычитание. Тип данных - это не то, как данные выглядят, а то, что с ними можно делать.

## Абстракция

Абстракция прячет детали за простым интерфейсом. Автомобиль скрывает двигатель за панелью управления - водителю не нужно разбираться в машиностроении, чтобы повернуть руль.

В программировании то же самое. Одной строкой

```python
html = fetch_source("https://tusur.ru/ru")
```

мы получаем страницу сайта, хотя за этой строкой стоят разрешение доменного имени, создание сокета и установка зашифрованного соединения. Всё это спрятано за именем `fetch_source`.

## Абстрактный тип данных

**Абстрактный тип данных (АТД)** - это описание группы операций над данными определённого типа, без деталей того, как данные хранятся в памяти. АТД отвечает на вопрос "что можно делать", а не "как это устроено внутри".

Возьмём **стек**. Это коллекция, работающая по принципу **LIFO** (last in, first out) - последним пришёл, первым вышел, как стопка тарелок: кладёте сверху, сверху и берёте.

АТД стека - две операции:

- `push(e)` - положить элемент на вершину;
- `pop()` - снять элемент с вершины.

Больше со стеком ничего делать нельзя, и это не ограничение, а удобство: раз переменная - стек, мы всегда знаем, что элементы обрабатываются строго в порядке "последний первым". Стек - это то, что стоит за кнопкой "Отменить" в текстовом редакторе: каждая правка кладётся на вершину, отмена снимает последнюю.

![Стек: кладём и снимаем сверху](images/stack.svg#only-light)
![Стек: кладём и снимаем сверху](images/stack.dark.svg#only-dark)

**Очередь** - второй базовый АТД, работающий по принципу **FIFO** (first in, first out) - первым пришёл, первым вышел, как живая очередь в магазине. Операции: `enqueue(e)` (встать в конец) и `dequeue()` (выйти из начала).

![Очередь: первым пришёл, первым вышел](images/queue.svg#only-light)
![Очередь: первым пришёл, первым вышел](images/queue.dark.svg#only-dark)

**Дек** (deque, double-ended queue - двусторонняя очередь) разрешает и то и другое: добавлять и снимать элементы можно с обоих концов. Стек и очередь - частные случаи дека: стек пользуется одним концом, очередь кладёт в один конец и берёт из другого.

Заметьте: нигде не сказано, *как именно* хранить элементы в памяти. Это и есть смысл АТД - интерфейс отделён от реализации. Один и тот же АТД можно реализовать по-разному, и на этом занятии мы так и сделаем. Вот что нас ждёт:

| АТД | Что умеет | Где реализуем |
| - | - | - |
| Стек | положить и снять сверху | задача 1 |
| Список | читать и менять элемент по номеру, расти в конце | часть 2, задача 2 |
| Очередь | встать в конец, выйти из начала | часть 4, разбор в тексте |
| Дек | класть и снимать с обоих концов | часть 4, задача 4 |
| Множество | добавить, удалить, проверить наличие | часть 5, разбор в тексте |
| Словарь | значение по ключу | часть 5, задача 5 |
| Очередь с приоритетом | выдать самый срочный элемент | часть 6, задача 6 |

Связные списки (часть 3, задача 3) - не отдельный АТД, а способ хранения, на котором можно построить почти любой из них.

# Часть 2. Массив и динамический массив

АТД описывает *что* можно делать, а **структура данных** - *как* данные лежат в памяти. Начнём с самой простой структуры.

## Массив

Массив - самый простой способ хранить набор элементов: единый непрерывный блок памяти, элементы записаны подряд. Если массив начинается с адреса $s$ и каждый элемент занимает $b$ байт, то $n$-й элемент лежит ровно по адресу $s + b \cdot n$.

Отсюда главное свойство массива - **мгновенный доступ по индексу** за $O(1)$: компьютер не ищет элемент, а вычисляет его адрес по формуле.

У непрерывности есть цена. Вставка или удаление в середине требует сдвинуть все последующие элементы - это $O(n)$. А размер блока выбирается при создании: рядом с массивом может лежать чужая память, и просто дописать ещё одну ячейку нельзя.

## Динамический массив

Но список Python растёт сколько угодно: `append` можно вызывать миллион раз. Как это сочетается с блоком фиксированного размера? Список Python - это **динамический массив**, и устроен он так:

- у массива есть **ёмкость** (capacity) - сколько ячеек выделено - и **размер** - сколько из них занято. Ёмкость обычно больше: про запас;
- пока запас есть, `append` просто пишет элемент в следующую свободную ячейку - $O(1)$;
- когда места нет, выделяется новый блок **вдвое больше**, все элементы копируются туда, а старый блок освобождается. Это стоит $O(n)$.

![Динамический массив: при переполнении всё копируется в блок вдвое больше](images/dynamic-array.svg#only-light)
![Динамический массив: при переполнении всё копируется в блок вдвое больше](images/dynamic-array.dark.svg#only-dark)

Выходит, что `append` иногда очень дорогой. Почему же говорят, что он работает за $O(1)$? Посчитаем, сколько всего копирований понадобится, чтобы добавить $n$ элементов в массив с начальной ёмкостью 4. Копирования случаются при переполнении на 4, 8, 16 и так далее элементах:

$$4 + 8 + 16 + \ldots + \frac{n}{2} < n.$$

Каждое слагаемое вдвое больше предыдущего, поэтому вся сумма меньше последнего слагаемого, умноженного на два, то есть меньше $n$. Вместе с самими записями выходит меньше $2n$ действий на $n$ вызовов - в среднем меньше двух на каждый. Такая оценка называется **амортизированной**: редкая дорогая операция "размазывается" по многим дешёвым, и в среднем каждая стоит $O(1)$.

Важно, что ёмкость растёт **во сколько-то раз**, а не на сколько-то ячеек. Если добавлять по 10 ячеек, копирований будет $10 + 20 + 30 + \ldots + n \approx \frac{n^2}{20}$: для миллиона элементов это $5 \cdot 10^{10}$ копирований вместо миллиона. Список Python растёт не вдвое, а примерно на одну восьмую, но главное то же самое - рост пропорционален размеру, и оценка остаётся $O(1)$.

Теперь понятно, почему стек из задачи 1 работает с концом списка: `append` и `pop()` на конце не сдвигают ни одного элемента. А `insert(0, x)` и `pop(0)` сдвигают все остальные элементы - это $O(n)$.

Реализуйте динамический массив своими руками. Внутри храните список Python **фиксированной длины**: создайте его как `[None] * capacity` и дальше только читайте и записывайте ячейки по индексу. Методы `append`, `insert`, `pop` и `extend` у внутреннего списка не вызывайте - иначе вы спрячете за ним ровно тот механизм, который нужно построить.

- `DynamicArray()` - пустой массив ёмкости 4.
- `capacity` - свойство только для чтения: текущая ёмкость.
- `append(item)` - добавить элемент в конец. Если места нет, сначала выделите блок вдвое больше и перепишите в него элементы.
- `pop()` - снять и вернуть последний элемент. Пустой массив - `IndexError`. Ёмкость при этом не уменьшается.
- `a[i]` и `a[i] = x` - методы `__getitem__` и `__setitem__`. Индекс должен быть от 0 до `len(a) - 1`, иначе `IndexError`. Отрицательные индексы не поддерживаются - тоже `IndexError`.

```python
a = DynamicArray()

for x in range(5):
    a.append(x * 10)
len(a)            # 5
a.capacity        # 8 - пятому элементу не хватило места
a[4]              # 40
a[1] = 99
a[1]              # 99
a.pop()           # 40
len(a)            # 4
a.capacity        # 8
a[4]              # IndexError - ячейка есть, но элемента в ней нет
```

# Часть 3. Связные списки

Динамический массив хорош всем, кроме вставки и удаления в начале и в середине: там приходится сдвигать хвост. Связный список устроен иначе.

## Связный список

Связный список хранит элементы в отдельных ячейках - **узлах**, разбросанных по памяти. Каждый узел содержит значение и **указатель на следующий** узел; конец цепи помечен пустым указателем. В Python указатель - это просто ссылка на другой объект, а пустой указатель - `None`.

![Массив и связный список](images/array-linked.svg#only-light)
![Массив и связный список](images/array-linked.dark.svg#only-dark)

Связный список не требует непрерывной памяти и легко растёт: новый узел может жить где угодно, достаточно переставить указатели. Вставка и удаление в середине - за $O(1)$, если известен узел рядом.

![Вставка в связный список](images/linked-list-insert.svg#only-light)
![Вставка в связный список](images/linked-list-insert.dark.svg#only-dark)

Плата - доступ по индексу: чтобы добраться до $n$-го узла, надо пройти по цепочке от начала, это $O(n)$.

## Односвязный список своими руками

Соберём односвязный список целиком. Узел - маленький класс с двумя атрибутами:

```python
class Node:
    def __init__(self, data, next=None):
        self.data = data            # значение
        self.next = next            # следующий узел или None
```

Сам список хранит только ссылку на первый узел - **голову** (`head`). Пустой список - это `head = None`. Всё остальное достижимо от головы по цепочке `next`.

```python
class LinkedList:
    def __init__(self):
        self.head = None

    def prepend(self, data):
        self.head = Node(data, self.head)

    def append(self, data):
        node = Node(data)
        if self.head is None:
            self.head = node
            return
        last = self.head
        while last.next is not None:
            last = last.next
        last.next = node

    def delete(self, data):
        prev = None
        node = self.head
        while node is not None and node.data != data:
            prev = node
            node = node.next
        if node is None:
            return                  # такого значения нет
        if prev is None:
            self.head = node.next   # удаляем голову
        else:
            prev.next = node.next   # предыдущий узел перешагивает через удаляемый

    def to_list(self):
        result = []
        node = self.head
        while node is not None:
            result.append(node.data)
            node = node.next
        return result
```

Разберём методы по очереди.

- **`prepend`** - вставка в начало. Новый узел получает в `next` старую голову и сам становится головой. Одна строка, $O(1)$, и она верна даже для пустого списка: тогда `self.head` равно `None`, и новый узел просто замыкает цепочку.
- **`to_list`** - обход. Переменная `node` идёт от головы по ссылкам `next`, пока не упрётся в `None`. Это главный приём работы со связным списком: почти каждый метод - такой же обход с разными действиями внутри.
- **`append`** - вставка в конец. Пустой список - особый случай: новый узел становится головой. Иначе обходом ищем последний узел (у него `next` равно `None`) и подвешиваем новый узел к нему. Обход стоит $O(n)$.
- **`delete`** - удаление первого узла со значением `data`. Обходом ищем узел, но держим в `prev` **предыдущий** узел: в односвязном списке от узла нельзя вернуться назад, а менять придётся именно указатель предыдущего. Дальше три случая: узел не найден - ничего не делаем; удаляется голова (`prev` равно `None`) - головой становится следующий узел; иначе предыдущий узел начинает указывать через удаляемый на следующий. Удалённый узел больше никто не видит, и Python освободит его память.

Проследим `delete(2)` для списка `1 -> 2 -> 3`:

![Удаление из односвязного списка: обход с указателем prev и перешагивание через узел](images/linked-list-delete.svg#only-light)
![Удаление из односвязного списка: обход с указателем prev и перешагивание через узел](images/linked-list-delete.dark.svg#only-dark)

| Шаг | `prev` | `node` | Что происходит |
| - | - | - | - |
| 1 | `None` | узел 1 | 1 не равно 2, сдвигаемся |
| 2 | узел 1 | узел 2 | нашли |
| 3 | узел 1 | узел 2 | `prev.next = node.next`: узел 1 теперь указывает на узел 3 |

```python
lst = LinkedList()
lst.append(1)
lst.append(2)
lst.append(3)
lst.prepend(0)
lst.to_list()      # [0, 1, 2, 3]
lst.delete(2)
lst.to_list()      # [0, 1, 3]
lst.delete(0)      # удаляем голову
lst.to_list()      # [1, 3]
lst.delete(42)     # такого значения нет - ничего не меняется
lst.to_list()      # [1, 3]
```

Итог по сложности:

| Операция | Односвязный список | Динамический массив |
| - | - | - |
| вставка в начало | $O(1)$ | $O(n)$ |
| вставка в конец | $O(n)$, с указателем на хвост $O(1)$ | $O(1)$ амортизированно |
| удаление найденного узла | $O(1)$, если известен предыдущий | $O(n)$ |
| доступ по индексу | $O(n)$ | $O(1)$ |

Вставку в конец легко ускорить: храните, кроме головы, ссылку на последний узел - **хвост** (`tail`). Тогда обход не нужен. Но у односвязного списка остаётся неустранимая слабость: от узла нельзя шагнуть назад. Удалить последний узел за $O(1)$ не получится даже с хвостом - чтобы отцепить его, нужен предпоследний, а его можно найти только обходом с головы.

> **Проверьте себя:** известен только сам узел в середине списка, без доступа к предыдущему. Как его удалить? Это известная задача с собеседований: скопировать в узел данные следующего и удалить следующий. Почему этот трюк не работает для последнего узла?

## Двусвязный список

В **двусвязном** списке у каждого узла два указателя: `next` на следующий и `prev` на предыдущий. Сам список хранит и голову, и хвост.

![Двусвязный список: узлы связаны в обе стороны, у списка есть голова и хвост](images/doubly-linked.svg#only-light)
![Двусвязный список: узлы связаны в обе стороны, у списка есть голова и хвост](images/doubly-linked.dark.svg#only-dark)

Что это даёт:

- список можно обходить в обе стороны: от головы по `next` и от хвоста по `prev`;
- вставка и в начало, и в конец - за $O(1)$;
- узел, на который у вас есть ссылка, удаляется за $O(1)$: его соседи известны из самого узла, и искать предыдущий не нужно.

Удаление узла сводится к тому, что соседи начинают смотреть друг на друга: `node.prev.next = node.next` и `node.next.prev = node.prev`. Если соседа слева нет, узел был головой - тогда вместо первого присваивания головой становится `node.next`. Если нет соседа справа, так же обновляется хвост.

Плата - лишний указатель в каждом узле и вдвое больше присваиваний при каждой вставке и удалении: больше памяти и больше мест, где можно ошибиться. Зато на двусвязном списке строятся вещи, которые без него медленны. Например, LRU-кэш из балльных задач: ему нужно за $O(1)$ вытаскивать элемент из середины и переносить в конец.

### 📝 Задача 3. Двусвязный список

> **Файл:** `dll.py` | **Классы:** `Node`, `DoublyLinkedList`

- `Node(data, next=None, prev=None)` - узел с атрибутами `data`, `next` и `prev`.
- `DoublyLinkedList()` - пустой список. Атрибуты `head` и `tail` - первый и последний узлы, у пустого списка оба `None`.

# Часть 4. Кольцевой буфер

Вернёмся к очереди. Если хранить её в списке Python, `enqueue` - это `append` за $O(1)$, но `dequeue` - это `pop(0)`, который сдвигает все оставшиеся элементы: $O(n)$. На очереди из ста тысяч элементов это сто тысяч сдвигов на каждый выход.

Первая мысль - не сдвигать, а запомнить индекс начала очереди `head` и при выходе просто увеличивать его. Но тогда начало массива навсегда остаётся пустым, а конец всё растёт: очередь медленно "уползает" вправо.

Решение - замкнуть массив в кольцо. Пусть после последней ячейки идёт ячейка 0. Очередь занимает `size` ячеек подряд, начиная с `head`, и, дойдя до конца массива, продолжается с начала. Элемент с номером `i` от начала очереди лежит в ячейке

$$(head + i) \bmod capacity,$$

а следующий элемент встанет в ячейку $(head + size) \bmod capacity$. Такую структуру называют **кольцевым буфером**.

![Кольцевой буфер: очередь a, b, c, d, e продолжается с начала массива](images/ring-buffer.svg#only-light)
![Кольцевой буфер: очередь a, b, c, d, e продолжается с начала массива](images/ring-buffer.dark.svg#only-dark)

Обе операции очереди теперь стоят $O(1)$: `enqueue` пишет в ячейку за концом очереди, `dequeue` сдвигает `head` на одну ячейку по кругу. Ничего не копируется.

## Очередь на кольцевом буфере своими руками

Когда кольцо заполнено, поступаем как динамический массив: выделяем блок вдвое больше. Но скопировать ячейки один в один нельзя. На рисунке выше очередь `a, b, c, d, e` занимает ячейки 5, 6, 7, 0, 1. Если переписать их в новый массив на те же места, между `e` и `a` окажутся пустые ячейки 8-15, и порядок сломается. Поэтому при росте очередь **разворачивается**: элементы переписываются по порядку, начиная с `head`, в ячейки 0, 1, 2 и так далее, а `head` становится 0.

```python
class Queue:
    def __init__(self):
        self._data = [None] * 4     # кольцо фиксированной длины
        self._head = 0              # ячейка первого элемента
        self._size = 0              # сколько элементов в очереди

    def is_empty(self):
        return self._size == 0

    def size(self):
        return self._size

    def _grow(self):
        bigger = [None] * (2 * len(self._data))
        for i in range(self._size):
            bigger[i] = self._data[(self._head + i) % len(self._data)]
        self._data = bigger
        self._head = 0

    def enqueue(self, item):
        if self._size == len(self._data):
            self._grow()
        self._data[(self._head + self._size) % len(self._data)] = item
        self._size += 1

    def front(self):
        if self._size == 0:
            raise IndexError("queue is empty")
        return self._data[self._head]

    def dequeue(self):
        item = self.front()
        self._data[self._head] = None           # не держим ссылку на ушедший элемент
        self._head = (self._head + 1) % len(self._data)
        self._size -= 1
        return item
```

Разберём, что здесь важно.

- Состояние очереди - три атрибута: кольцо `_data`, начало `_head` и размер `_size`. Индекс конца не хранится: он всегда вычисляется как `(_head + _size) % len(_data)`. Чем меньше хранится, тем меньше того, что может разойтись.
- `enqueue` при полном кольце сначала растит его, потом пишет в ячейку за концом очереди.
- `dequeue` переиспользует `front`: проверка пустоты и чтение первого элемента написаны один раз. Затем освобождает ячейку и сдвигает `head` по кругу: из ячейки 7 кольца на 8 ячеек `head` переходит в ячейку 0.
- `_grow` разворачивает очередь в новый массив по порядку, как описано выше.

```python
q = Queue()
for x in "abcd":
    q.enqueue(x)
q.dequeue()        # 'a'
q.dequeue()        # 'b'
q.enqueue("e")     # ячейка 0 освободилась - "e" встаёт туда
q.enqueue("f")
q._data            # ['e', 'f', 'c', 'd']
q.enqueue("g")     # места нет: кольцо растёт и разворачивается
q._data            # ['c', 'd', 'e', 'f', 'g', None, None, None]
q.front()          # 'c'
q.size()           # 5
```

![Очередь на кольцевом буфере в примере: выход без сдвигов, переход через край, рост с разворотом](images/ring-queue-steps.dark.svg#only-dark)

Обращаться к `_data` снаружи не принято - здесь это сделано, только чтобы заглянуть внутрь.

В стандартной библиотеке Python готовая очередь - это `collections.deque` (смотрите [Python-конспект](python.md)). Устроена она немного иначе: как двусвязный список блоков по 64 элемента. Но обещание то же - $O(1)$ на обоих концах.

## Дек

Кольцевой буфер легко сделать двусторонним. Добавить в конец и снять с начала мы уже умеем. Снять с конца - уменьшить `size`. Добавить в начало - сдвинуть `head` на одну ячейку **назад** по кругу: `(head - 1) % capacity`. В Python остаток от деления на положительное число никогда не бывает отрицательным: `(0 - 1) % 8` равно 7, то есть из ячейки 0 мы попадаем в последнюю ячейку, как и нужно.

# Часть 5. Хеш-таблица

Словарь и множество в Python находят элемент за $O(1)$ - быстрее, чем любая структура на сравнении. Секрет - в **хеш-таблице**.

Идея проста. Заводим массив "кармашков" (buckets). Специальная **хеш-функция** превращает значение в номер кармашка, и элемент кладётся именно туда. Поиск - это снова вычислить хеш-функцию и заглянуть в один кармашек: сколько бы элементов ни было, шагов всегда одно и то же число.

![Хеш-таблица](images/hash-table.svg#only-light)
![Хеш-таблица](images/hash-table.dark.svg#only-dark)

У простой схемы есть подвох: два разных значения могут получить одинаковый номер кармашка. Это **коллизия**. Коллизии решают, например, цепочками: в одном кармашке лежит список элементов с одинаковым номером, и при поиске его проходят подряд.

Отсюда два правила хорошей хеш-таблицы:

1. **Хеш-функция разбрасывает значения равномерно** - тогда цепочки остаются короткими.
2. **Кармашков должно быть с запасом** - если таблица забита почти под завязку, коллизии случаются постоянно и поиск вырождается в $O(n)$.

Отношение числа элементов к числу кармашков называют **коэффициентом заполнения**. Словарь Python следит, чтобы он не превышал примерно $\frac{2}{3}$: когда элементов становится больше, таблица выделяет больше кармашков и раскладывает всё заново. Это та же идея, что у динамического массива, и та же амортизированная оценка $O(1)$.

Хеш-функцию писать не нужно: в Python есть встроенная `hash`. Она превращает любое неизменяемое значение в целое число, а номер кармашка получается остатком от деления:

```python
hash(10)           # 10 - небольшое целое число и есть свой хеш
hash(10) % 10      # 0
hash(20) % 10      # 0 - коллизия: 10 и 20 попадут в один кармашек
hash("кот") == hash("кот")    # True - одинаковые значения, одинаковый хеш
```

Хеш строки меняется от запуска к запуску программы - так Python защищается от атак, которые подбирают ключи с одинаковым хешем. Внутри одного запуска он постоянен, и этого достаточно.

## Множество на хеш-таблице своими руками

Множество - самая простая хеш-таблица: в кармашках лежат сами значения.

```python
class HashSet:
    def __init__(self, size=10):
        self._buckets = [[] for _ in range(size)]
        self._count = 0

    def _bucket(self, value):
        return self._buckets[hash(value) % len(self._buckets)]

    def add(self, value):
        bucket = self._bucket(value)
        if value not in bucket:
            bucket.append(value)
            self._count += 1

    def remove(self, value):
        bucket = self._bucket(value)
        if value in bucket:
            bucket.remove(value)
            self._count -= 1

    def contains(self, value):
        return value in self._bucket(value)

    def __len__(self):
        return self._count
```

Разберём.

- `[[] for _ in range(size)]` создаёт `size` **разных** пустых списков. Запись `[[]] * size` здесь ошибочна: она создала бы `size` ссылок на **один** список, и все значения свалились бы в один кармашек (помните ярлыки и объекты из занятия 4.1).
- `_bucket` - единственное место, где вычисляется номер кармашка. Все три операции начинают с него: вычислили номер, дальше работаем с одним коротким списком, а остальные кармашки не трогаем.
- `value in bucket` перебирает только свой кармашек. Пока цепочки короткие, это несколько сравнений.
- Счётчик `_count` растёт и уменьшается только тогда, когда значение действительно добавилось или удалилось: повторный `add` ничего не меняет.

```python
s = HashSet()
s.add(10)
s.add(20)          # коллизия: тот же кармашек 0, но 10 не потерялось
s.add(20)          # повторно не добавляется
len(s)             # 2
s.contains(10)     # True
s.remove(10)
s.contains(10)     # False
s.contains(20)     # True
```

Таблица из 10 кармашков не растёт. Положите в неё миллион чисел - и в каждом кармашке окажется цепочка в сто тысяч элементов, поиск станет $O(n)$. Настоящая хеш-таблица растёт, как описано выше.

## Словарь - АТД "ключ - значение"

Словарь хранит пары "ключ - значение" и умеет:

- `put(key, value)` - запомнить значение по ключу, а если ключ уже есть - заменить значение;
- `get(key)` - достать значение по ключу;
- `remove(key)` - удалить пару;
- `contains(key)` - есть ли такой ключ.

Устроен он как множество, только в кармашке лежат пары `[ключ, значение]`, а номер кармашка считается **по ключу**. При поиске мы приходим в кармашек по хешу ключа и сравниваем ключи через `==`: в одном кармашке могут оказаться разные ключи с одинаковым номером.

Поэтому ключ обязан быть **неизменяемым**. Представьте, что ключом стал список `[1, 2]`, а потом в него дописали тройку. Хеш изменился, но пара так и лежит в кармашке, вычисленном по старому хешу, - её больше никогда не найти. Поэтому Python и не разрешает делать списки ключами словаря.

# Часть 6. Очередь с приоритетом

В обычной очереди первым выходит тот, кто раньше пришёл. Но в приёмном покое первым принимают не того, кто раньше пришёл, а того, кому хуже: остановка сердца важнее пореза пальца. **Очередь с приоритетом** - АТД, в котором у каждого элемента есть **приоритет**, и выходит всегда самый срочный элемент. Договоримся, что срочнее тот, у кого приоритет **меньше**: 1 - срочно, 3 - подождёт.

Операции:

- `push(item, priority)` - добавить элемент с приоритетом;
- `pop()` - снять и вернуть самый срочный элемент;
- `peek()` - посмотреть на самый срочный, не снимая.

Если приоритеты равны, честно отпускать в порядке прихода: двое с одинаковым порезом пальца идут к врачу по очереди. Такие очереди повсюду: операционная система выбирает, какой программе дать процессор, принтер печатает срочные документы раньше, игра обрабатывает события по времени.

## Две реализации на списке

Будем хранить пары `(приоритет, элемент)` в обычном списке. Остаётся решить, поддерживать ли в нём порядок.

**Неотсортированный список.** `push` дописывает пару в конец - $O(1)$. Зато `pop` должен найти самый срочный элемент линейным поиском, как в занятии 3, - $O(n)$, и ещё $O(n)$ уходит на то, чтобы вынуть его из середины списка. Порядок прихода при этом сохраняется сам собой: если при поиске минимума заменять кандидата только на **строго** меньший приоритет, среди равных останется тот, кто стоит раньше, то есть пришёл раньше.

**Отсортированный список.** Держим пары упорядоченными так, чтобы самый срочный элемент лежал **в конце**. Тогда `pop` - это `pop()` с конца, $O(1)$. Зато `push` должен найти новому элементу место - ровно как один шаг сортировки вставками из занятия 3 - и вставить его со сдвигом, $O(n)$. Чтобы сохранить порядок прихода, новичок встаёт **за** всеми элементами с тем же приоритетом, то есть ближе к началу списка.

| Реализация | `push` | `pop` | `peek` |
| - | - | - | - |
| неотсортированный список | $O(1)$ | $O(n)$ | $O(n)$ |
| отсортированный список | $O(n)$ | $O(1)$ | $O(1)$ |

Какую выбрать, зависит от того, каких операций больше. Если элементы сыплются потоком, а забирают их редко, выгоднее первая. Если очередь заполняется один раз, а потом часто спрашивают самый срочный - вторая. Обе тратят $O(n)$ на одну из операций. В главе 7 появится куча - структура, где и `push`, и `pop` стоят $O(\log n)$.

Одна ловушка - общая для обеих реализаций. Кортежи в Python сравниваются поэлементно: при равных приоритетах `(3, a) < (3, b)` начнёт сравнивать сами элементы. Если элементы - словари или другие несравнимые объекты, получится `TypeError`, а если сравнимые - порядок прихода тихо нарушится. Поэтому сравнивайте **только приоритеты**: `pair[0] < best[0]`, а не `pair < best`.

### 📝 Задача 6. Очередь с приоритетом

> **Файл:** `priority_queue.py` | **Класс:** `PriorityQueue`

Реализуйте очередь с приоритетом на списке. Какую из двух реализаций выбрать - решать вам. Модуль `heapq` и `queue.PriorityQueue` использовать нельзя.

- `PriorityQueue()` - пустая очередь.
- `push(item, priority)` - добавить элемент. Приоритет - число; чем меньше, тем срочнее.
- `pop()` - снять и вернуть элемент с наименьшим приоритетом. При равных приоритетах - тот, что добавлен раньше. Пустая очередь - `IndexError`.
- `peek()` - вернуть тот же элемент, не снимая. Пустая очередь - `IndexError`.
- `__len__` - число элементов, `is_empty()` - пуста ли очередь.
- Элементы могут быть чем угодно, в том числе несравнимыми объектами вроде словарей.

```python
er = PriorityQueue()
er.push("порез пальца", 3)
er.push("перелом", 2)
er.push("остановка сердца", 1)
er.push("ушиб", 3)
er.peek()          # 'остановка сердца'
er.pop()           # 'остановка сердца'
er.pop()           # 'перелом'
er.pop()           # 'порез пальца' - пришёл раньше ушиба
len(er)            # 1
```

| Структура | Быстро | Медленно |
| - | - | - |
| динамический массив | доступ по индексу, добавление и снятие в конце: $O(1)$ | вставка и удаление в начале и в середине: $O(n)$ |
| двусвязный список | вставка и удаление на концах и рядом с известным узлом: $O(1)$ | доступ по индексу и поиск: $O(n)$ |
| кольцевой буфер | добавление и снятие на обоих концах: $O(1)$ | вставка в середину: $O(n)$ |
| хеш-таблица | добавление, поиск и удаление: $O(1)$ в среднем | порядок элементов не хранит |
| очередь с приоритетом на списке | одна из двух операций: $O(1)$ | другая: $O(n)$ |
