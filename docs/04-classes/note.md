# Часть 1. Задача, которой не хватает типов

Ландшафтный дизайнер рисует план участка: круглые клумбы и прямоугольные газоны. Для сметы нужны две цифры: сколько покупать земли (суммарная площадь) и сколько бордюра (суммарный периметр).

Опишем фигуры тем, что уже знаем. Круг задаётся центром и радиусом, прямоугольник - левым нижним углом, шириной и высотой. Фигур много, поэтому заводим списки:

```python
import math

circle_x = [0, 6]
circle_y = [0, 2]
circle_r = [1, 2]

rect_x = [10, 0]
rect_y = [0, 5]
rect_w = [4, 3]
rect_h = [2, 3]

area = 0
for i in range(len(circle_r)):
    area += math.pi * circle_r[i] ** 2
for i in range(len(rect_w)):
    area += rect_w[i] * rect_h[i]

round(area, 2)   # 32.71
```

Работает. Но посмотрите, что будет, когда программа начнёт расти.

**Одна фигура размазана по нескольким спискам.** Клумба номер 1 - это `circle_x[1]`, `circle_y[1]` и `circle_r[1]`, и ничто, кроме вашей аккуратности, не связывает их вместе. Удалили клумбу из `circle_x` и `circle_y`, а про `circle_r` забыли - радиусы съехали на соседние клумбы. Ошибки нет, программа молча считает чепуху.

**Функции обрастают параметрами.** Сдвинуть круг - это `move_circle(circle_x, circle_y, i, dx, dy)`: пять аргументов, чтобы подвинуть одну фигуру. А вызов `draw(3, 4, 7, 1)` невозможно прочитать без документации: где тут центр, а где радиус?

**Новый вид фигуры ломает всё.** Треугольник - это ещё несколько списков и новый цикл в каждой функции: в площади, в периметре, в отрисовке.

![Одна фигура в трёх списках и одна фигура - один объект](images/scattered.svg#only-light)
![Одна фигура в трёх списках и одна фигура - один объект](images/scattered.dark.svg#only-dark)

Можно собрать каждую фигуру в словарь:

```python
figures = [
    {"kind": "circle", "x": 0, "y": 0, "r": 1},
    {"kind": "circle", "x": 6, "y": 2, "r": 2},
    {"kind": "rect", "x": 10, "y": 0, "w": 4, "h": 2},
    {"kind": "rect", "x": 0, "y": 5, "w": 3, "h": 3},
]

def figure_area(figure):
    if figure["kind"] == "circle":
        return math.pi * figure["r"] ** 2
    elif figure["kind"] == "rect":
        return figure["w"] * figure["h"]

total = 0
for f in figures:
    total += figure_area(f)

round(total, 2)   # 32.71
```

Стало лучше: одна фигура - одно значение, удалить клумбу можно одной операцией. Но две проблемы остались.

- **Никто не следит за содержимым.** Ничто не мешает написать `{"kind": "circle", "radius": 1}` вместо `"r"` или `{"kind": "circle", "r": -5}`. Опечатка всплывёт `KeyError` где-то глубоко в расчётах, а отрицательный радиус не всплывёт вообще.
- **Знание о том, что такое круг, разбросано по программе.** Формула площади живёт в `figure_area`, периметра - в `figure_perimeter`, отрисовки - в `draw`, и в каждой функции одна и та же лестница `if figure["kind"] == ...`. Добавить треугольник - значит пройти по всем функциям и в каждую вписать ещё одну ветку. Забудете одну - узнаете об этом от пользователя.

Сформулируем, чего мы хотим.

1. Фигура - **одно значение** с именованными полями.
2. Правила, относящиеся к кругу (формула площади, "радиус положителен"), **живут рядом с данными круга**, а не разбросаны по программе.
3. Код, который считает смету, **не знает, какие бывают фигуры**: ему достаточно, что у любой фигуры можно спросить площадь.

Именно это дают классы. К концу занятия смета будет считаться так:

```python
plan = [Circle(0, 0, 1), Circle(6, 2, 2), Rectangle(10, 0, 4, 2), Rectangle(0, 5, 3, 3)]

total = 0
for figure in plan:
    total += figure.area()
```

и этот цикл не изменится ни на символ, когда в плане появятся треугольники.

Принцип, который стоит за первыми двумя пунктами, называется **инкапсуляцией**: всё, что описывает один объект, - и данные, и операции над ними - хранится вместе. Это правило не привязано к объектно-ориентированному программированию (ООП) и не зависит от языка, а классы - самый удобный способ ему следовать.

# Часть 2. Класс и объект

Вы пользуетесь объектами с первого занятия:

```python
type(5)            # <class 'int'>
type("кот")        # <class 'str'>
"кот".upper()      # 'КОТ'
```

В Python **всё - объект**: число, строка, список, даже функция. У каждого объекта есть тип, и тип определяет, что с объектом можно делать: у строки есть метод `upper`, у числа - нет. Слово `class` в ответе `type` не случайно: `int` и `str` - тоже классы, просто встроенные.

**Класс** - это описание нового типа: какие данные хранит каждый объект (**атрибуты**) и что он умеет (**методы**). **Объект**, или **экземпляр**, - конкретное значение этого типа. Класс `Circle` - это "круг вообще", а `Circle(0, 0, 1)` - вот этот круг с центром в нуле.

```python
import math


class Circle:
    def __init__(self, x, y, r):
        self.x = x
        self.y = y
        self.r = r

    def area(self):
        return math.pi * self.r ** 2

    def perimeter(self):
        return 2 * math.pi * self.r

    def move(self, dx, dy):
        self.x += dx
        self.y += dy
```

Разберём по строкам.

- `class Circle:` - объявление нового типа. Имена классов пишут с большой буквы: `Circle`, `BankAccount`.
- `def` внутри класса - **метод**: функция, которая принадлежит классу и работает с конкретным объектом.
- `__init__` - **конструктор**. Python вызывает его сам, когда создаётся объект. Задача конструктора - задать начальное состояние: заполнить атрибуты.
- `self` - первый параметр каждого метода, ссылка на тот самый объект, с которым метод работает. `self.r = r` значит "у этого круга радиус равен `r`".

Создаём объекты и пользуемся ими:

```python
a = Circle(0, 0, 1)
b = Circle(6, 2, 2)

a.r               # 1
b.r               # 2
a.area()          # 3.141592653589793
b.perimeter()     # 12.566370614359172
a.move(2, 3)
(a.x, a.y)        # (2, 3)
```

Когда вы пишете `Circle(0, 0, 1)`, Python создаёт пустой объект и вызывает `__init__(объект, 0, 0, 1)`. Когда пишете `a.area()`, Python вызывает `Circle.area(a)`: объект слева от точки становится `self`. Поэтому в объявлении метода `self` есть, а в вызове его нет.

У каждого объекта свои атрибуты: `a` и `b` созданы по одному чертежу, но радиусы у них разные, и `a.move` сдвинул только `a`.

## Конструктор охраняет правила

Вспомним отрицательный радиус. Конструктор - единственная дверь, через которую объект появляется на свет, значит, проверять данные нужно именно в нём:

```python
class Circle:
    def __init__(self, x, y, r):
        if r <= 0:
            raise ValueError("радиус должен быть положительным")
        self.x = x
        self.y = y
        self.r = r

    ...   # area, perimeter, move - как раньше
```

`raise` **поднимает исключение**: выполнение немедленно прерывается, а вызывающий код получает ошибку с понятным текстом. Объект при этом так и не создаётся:

```python
Circle(0, 0, -5)   # ValueError: радиус должен быть положительным
```

Вернуть "не получилось" конструктор не может - он вообще ничего не возвращает. Исключение - единственный способ сказать "такого объекта быть не может".

Правило "радиус положителен" называют **инвариантом** класса: условием, которое верно для любого объекта в любой момент. Конструктор обеспечивает инвариант при рождении объекта, а методы не должны нарушать его потом.

## Исключения: самое необходимое

Исключение - это сигнал "дальше так нельзя". Его поднимают командой `raise`, указывая тип ошибки и понятный человеку текст: `raise ValueError("радиус должен быть положительным")`. Дальше происходит вот что:

- выполнение функции немедленно прерывается, строки после `raise` не выполняются;
- исключение "всплывает" к тому, кто вызвал функцию, от него - к тому, кто вызвал его, и так далее;
- если по дороге исключение никто не поймал, программа останавливается и печатает тип ошибки, текст и строку, где всё случилось.

Поймать исключение можно конструкцией `try` / `except`:

```python
try:
    c = Circle(0, 0, -5)
except ValueError as e:
    print("не получилось:", e)   # не получилось: радиус должен быть положительным
```

Код в `try` выполняется как обычно. Если внутри поднялось исключение указанного типа, выполнение переходит в блок `except`, а в переменной `e` оказывается само исключение вместе с текстом. Программа при этом не падает и идёт дальше.

Тип исключения выбирают по смыслу ошибки:

| Исключение | Когда поднимают |
| - | - |
| `ValueError` | значение недопустимо: отрицательный радиус, нехватка денег на счёте |
| `TypeError` | значение не того типа: вместо фигуры передали строку |
| `KeyError` | нет такого ключа: книги с таким ISBN в библиотеке нет |
| `AttributeError` | у объекта нет такого атрибута |

В задачах этого занятия нужный тип исключения всегда указан в условии. Как ловить несколько типов сразу и как объявить собственное исключение - в [Python-конспекте](python.md).

## Как объект выглядит при печати

```python
print(Circle(0, 0, 1))   # <__main__.Circle object at 0x7f3a...>
```

Python не знает, как показать круг, и печатает тип и адрес в памяти. Научим его - методом `__repr__`:

```python
class Circle:
    ...

    def __repr__(self):
        return f"Circle({self.x}, {self.y}, {self.r})"
```

```python
Circle(0, 0, 1)   # Circle(0, 0, 1)
```

Методы с двойным подчёркиванием с обеих сторон называют **специальными**: их почти никогда не вызывают руками, их вызывает сам Python в особых ситуациях. `__init__` - при создании объекта, `__repr__` - когда объект нужно превратить в строку. Хорошая традиция - чтобы `__repr__` возвращал строку, похожую на код, который создаёт такой же объект.

## Второй класс и смета

Прямоугольник устроен так же:

```python
class Rectangle:
    def __init__(self, x, y, w, h):
        if w <= 0 or h <= 0:
            raise ValueError("стороны должны быть положительными")
        self.x = x
        self.y = y
        self.w = w
        self.h = h

    def area(self):
        return self.w * self.h

    def perimeter(self):
        return 2 * (self.w + self.h)

    def move(self, dx, dy):
        self.x += dx
        self.y += dy

    def __repr__(self):
        return f"Rectangle({self.x}, {self.y}, {self.w}, {self.h})"
```

И вот смета из части 1:

```python
plan = [Circle(0, 0, 1), Circle(6, 2, 2), Rectangle(10, 0, 4, 2), Rectangle(0, 5, 3, 3)]

total = 0
for figure in plan:
    total += figure.area()

round(total, 2)   # 32.71
```

В цикле нет ни одного `if`. Он не спрашивает, круг перед ним или прямоугольник, а просто просит фигуру посчитать свою площадь, и каждая фигура считает по своей формуле. Третий пункт нашего списка желаний выполнился почти сам собой. В части 6 разберёмся, почему так вышло, и сделаем это надёжным.

# Часть 3. Интерфейс и внутреннее устройство

У счёта из задачи 1 есть дыра: ничто не мешает написать `acc.balance = 1_000_000`. Все проверки в `deposit` и `withdraw` обходятся одним присваиванием. С кругом то же самое: конструктор не пустит отрицательный радиус, но `c.r = -5` после создания пройдёт без вопросов.

В C++ и Java у атрибутов есть модификаторы доступа: `public`, `protected`, `private`, и компилятор не даёт тронуть закрытое поле снаружи. Python устроен на договорённостях:

| Имя | Смысл | Похоже на |
| - | - | - |
| `radius` | публичный атрибут, часть интерфейса - пользуйтесь | `public` |
| `_radius` | внутренний: "снаружи не трогать, это детали устройства" | `protected` |
| `__radius` | Python искажает имя в `_Circle__radius`, чтобы наследник не перекрыл его случайно | `private` |

Python не запрещает обратиться к `_radius`. Но если вы это сделали и всё сломалось, виноваты вы. В сообществе Python это формулируют так: "мы все здесь взрослые люди".

**Интерфейс** класса - это его публичные методы и атрибуты: то, чем пользуются снаружи. **Реализация** - всё остальное: как именно данные хранятся внутри. Хороший класс показывает наружу минимум и прячет остальное. Тогда реализацию можно менять, не ломая код, который пользуется классом. Например, сумму денег можно хранить парой "рубли и копейки", а можно одним числом копеек. Если снаружи доступны только методы, это решение можно пересмотреть в любой момент, и никто из пользователей класса не заметит подмены.

## Свойства: атрибут с проверкой

Хочется, чтобы `c.r` читался как обычный атрибут, а присваивание проверялось. Для этого есть **свойство** - декоратор `@property`:

```python
class Circle:
    def __init__(self, x, y, r):
        self.x = x
        self.y = y
        self.r = r          # присваивание пойдёт через сеттер ниже

    @property
    def r(self):
        return self._r

    @r.setter
    def r(self, value):
        if value <= 0:
            raise ValueError("радиус должен быть положительным")
        self._r = value

    ...   # area, perimeter, move, __repr__ - как раньше
```

```python
c = Circle(0, 0, 1)
c.r             # 1 - выглядит как атрибут, а на самом деле вызывает метод
c.r = 3         # проверка пройдена
c.r = -5        # ValueError: радиус должен быть положительным
```

`@property` превращает метод в атрибут для чтения: `c.r` без скобок вызывает метод `r`. `@r.setter` задаёт, что происходит при присваивании `c.r = ...`. Само значение хранится во внутреннем атрибуте `_r`, а проверка живёт в одном месте, и конструктор тоже проходит через неё.

Если сеттер не объявить, свойство будет **только для чтения**, и присваивание поднимет `AttributeError`. Так делают с тем, что нельзя менять напрямую, - например, с остатком на счёте:

```python
class Account:
    ...

    @property
    def balance(self):
        return self._balance
```

Теперь `acc.balance = 1_000_000` - ошибка, а остаток меняется только через `deposit` и `withdraw`, которые проверяют суммы.

## Специальные методы: свои типы ведут себя как встроенные

Сравним два одинаковых круга:

```python
Circle(0, 0, 1) == Circle(0, 0, 1)   # False
```

По умолчанию `==` для объектов проверяет, **один ли это объект**, а не равны ли они по смыслу. Здесь два разных объекта, пусть и одинаковых. Что значит "равны" для ваших объектов, решаете вы - методом `__eq__`:

```python
class Circle:
    ...

    def __eq__(self, other):
        return (self.x, self.y, self.r) == (other.x, other.y, other.r)
```

```python
Circle(0, 0, 1) == Circle(0, 0, 1)   # True
```

Точно так же устроены все операторы. Встречая `a < b`, Python вызывает `a.__lt__(b)`, а `len(a)` превращается в `a.__len__()`. Научим фигуры сравниваться по площади - и бесплатно получим `sorted`, `min` и `max`:

```python
class Circle:
    ...

    def __lt__(self, other):
        return self.area() < other.area()
```

```python
circles = [Circle(0, 0, 3), Circle(1, 1, 1), Circle(2, 2, 2)]
sorted(circles)    # [Circle(1, 1, 1), Circle(2, 2, 2), Circle(0, 0, 3)]
max(circles)       # Circle(0, 0, 3)
```

`sorted` и `max` ничего не знают о кругах. Они сравнивают элементы через `<`, а `<` для кругов теперь определён. В этом смысл специальных методов: ваш тип встраивается в язык наравне с `int` и `str`.

| Выражение | Что вызывает Python |
| - | - |
| `Circle(0, 0, 1)` | `__init__` |
| `repr(c)`, объект внутри списка | `__repr__` |
| `print(c)`, `str(c)` | `__str__`, а если его нет - `__repr__` |
| `a == b` | `a.__eq__(b)` |
| `a < b` | `a.__lt__(b)` |
| `a + b` | `a.__add__(b)` |
| `len(a)` | `a.__len__()` |
| `x in a` | `a.__contains__(x)` |

Остальные специальные методы - в [Python-конспекте](python.md).

# Часть 4. Объекты внутри объектов

У кругов и прямоугольников есть общее понятие - точка на плоскости. С точкой связаны свои операции: расстояние до другой точки, сдвиг. Значит, точка - кандидат в отдельный класс:

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def distance_to(self, other):
        return math.sqrt((self.x - other.x) ** 2 + (self.y - other.y) ** 2)

    def move(self, dx, dy):
        self.x += dx
        self.y += dy

    def __repr__(self):
        return f"Point({self.x}, {self.y})"
```

Атрибутом объекта может быть любой объект, в том числе объект вашего же класса. Отрезок - это две точки:

```python
class Segment:
    def __init__(self, start, end):
        self.start = start
        self.end = end

    def length(self):
        return self.start.distance_to(self.end)

    def __repr__(self):
        return f"Segment({self.start}, {self.end})"
```

```python
s = Segment(Point(0, 0), Point(3, 4))
s.length()     # 5.0
s.start.x      # 0 - у отрезка взяли начало, у начала - x
```

Так из простых классов собирают сложные. Но чтобы делать это без сюрпризов, нужно точно понимать, что хранит атрибут.

## Переменная - это ярлык, а не коробка

На втором занятии вы видели ловушку: `q2 = q1` не копирует список. С любыми объектами происходит то же самое, и это не ловушка, а то, как устроен Python:

```python
p = Point(0, 0)
q = p            # не копия! второе имя того же объекта
q.move(5, 0)
p                # Point(5, 0)
p is q           # True - это один объект
```

Переменная в Python - не коробка, в которой лежит значение, а **ярлык**, привязанный к объекту. Присваивание `q = p` не создаёт новую точку, а вешает на ту же точку второй ярлык. Оператор `is` проверяет, один ли это объект, а `==` - равны ли объекты по смыслу (если в классе определён `__eq__`).

![Два ярлыка на одном объекте](images/references.svg#only-light)
![Два ярлыка на одном объекте](images/references.dark.svg#only-dark)

То же самое при передаче объекта в функцию: параметр - ещё один ярлык на тот же объект, поэтому функция может объект изменить:

```python
def shift_right(point):
    point.move(1, 0)

p = Point(0, 0)
shift_right(p)
p                # Point(1, 0)
```

Атрибут объекта - тоже ярлык. Поэтому два отрезка могут ссылаться на одну и ту же точку:

```python
a = Point(0, 0)
b = Point(3, 4)
c = Point(6, 0)

ab = Segment(a, b)
bc = Segment(b, c)     # точка b общая у двух отрезков

b.move(0, 1)           # сдвинули вершину
(ab.end, bc.start)     # (Point(3, 5), Point(3, 5))
```

Для ломаной это ровно то, что нужно: вершина одна, и оба отрезка, сходящиеся в ней, двигаются вместе. Но если каждый отрезок должен владеть своими точками, общие ссылки становятся источником ошибок: сдвинули конец одного отрезка - поехал другой.

## Поверхностная и глубокая копия

Как скопировать отрезок, чтобы копию можно было менять независимо? Модуль `copy` предлагает два способа:

```python
import copy

s1 = Segment(Point(0, 0), Point(3, 4))
s2 = copy.copy(s1)        # поверхностная копия
s2.end.move(10, 0)
s1.end                    # Point(13, 4) - поехала и точка оригинала!
```

`copy.copy` создаёт новый объект-отрезок, но его атрибуты - те же ярлыки на те же точки. Отрезков два, а точки по-прежнему общие. Это **поверхностная копия**.

```python
s1 = Segment(Point(0, 0), Point(3, 4))
s3 = copy.deepcopy(s1)    # глубокая копия
s3.end.move(10, 0)
s1.end                    # Point(3, 4) - оригинал не тронут
```

`copy.deepcopy` копирует всё, до чего дотянется: новый отрезок и новые точки внутри него. Это **глубокая копия**.

![Поверхностная и глубокая копия отрезка](images/copy.svg#only-light)
![Поверхностная и глубокая копия отрезка](images/copy.dark.svg#only-dark)

Какая копия нужна, зависит от того, **кто владеет** вложенными объектами.

## Композиция и агрегация

**Композиция** - объект *состоит из* частей и владеет ими: части создаются вместе с ним и без него не имеют смысла. Комнаты принадлежат дому: снесли дом - нет и комнат. Если отрезок - самостоятельная фигура, он сам создаёт свои точки и никому их не отдаёт:

```python
class Segment:
    def __init__(self, x1, y1, x2, y2):
        self.start = Point(x1, y1)    # отрезок сам создаёт свои точки
        self.end = Point(x2, y2)
```

Такой объект копируют глубоко: у копии должны быть свои части.

**Агрегация** - объект *содержит* части, но не владеет ими: части приходят снаружи готовыми, живут своей жизнью и могут принадлежать нескольким владельцам сразу. Ломаная ссылается на общие вершины. Учебная группа состоит из студентов, но, когда группу расформировали, студенты никуда не делись. Такой объект копируют поверхностно, иначе копия группы породит клонов студентов.

![Композиция: отрезок владеет своими точками. Агрегация: отрезки ломаной делят общую вершину](images/composition-aggregation.svg#only-light)
![Композиция: отрезок владеет своими точками. Агрегация: отрезки ломаной делят общую вершину](images/composition-aggregation.dark.svg#only-dark)

В коде композиция и агрегация выглядят одинаково: атрибут ссылается на объект. Разница в том, **кто создаёт** вложенный объект и **может ли он быть общим**. Это решение принимаете вы, когда проектируете класс.

# Часть 5. Наследование

Посмотрим на `Circle` и `Rectangle` вместе. У обоих есть координаты `x` и `y`, одинаковый метод `move`, у обоих есть площадь и периметр. Код продублирован, и если понадобится, скажем, повернуть фигуру, придётся писать поворот дважды.

Можно ли считать круг частным случаем прямоугольника или наоборот? Нет: свойства одного не являются подмножеством свойств другого. Зато и круг, и прямоугольник - частные случаи третьего понятия, **фигуры**, которое собирает их общие черты. Так и запишем:

```python
class Shape:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def move(self, dx, dy):
        self.x += dx
        self.y += dy


class Circle(Shape):
    def __init__(self, x, y, r):
        super().__init__(x, y)
        self.r = r

    def area(self):
        return math.pi * self.r ** 2

    def perimeter(self):
        return 2 * math.pi * self.r


class Rectangle(Shape):
    def __init__(self, x, y, w, h):
        super().__init__(x, y)
        self.w = w
        self.h = h

    def area(self):
        return self.w * self.h

    def perimeter(self):
        return 2 * (self.w + self.h)
```

Проверки и `__repr__` здесь опущены, чтобы не загромождать пример.

- `class Circle(Shape)` - `Circle` **наследует** `Shape`: получает все его атрибуты и методы. `Shape` - **родительский**, или базовый, класс, `Circle` - **дочерний**, или наследник.
- `super().__init__(x, y)` - вызов конструктора родителя: он заполняет свою часть объекта, `x` и `y`. После этого наследник дописывает своё - радиус. Забудете `super().__init__` - у круга не будет `x` и `y`, и первый же `move` упадёт с `AttributeError`.

```python
c = Circle(0, 0, 1)
c.move(2, 3)              # метод унаследован от Shape
(c.x, c.y)                # (2, 3)
isinstance(c, Circle)     # True
isinstance(c, Shape)      # True - круг является фигурой
```

Наследование моделирует отношение **"является"**: круг *является* фигурой, поэтому всё, что умеет фигура, умеет и круг. Это хороший тест на то, уместно ли наследование. "Цветная точка является точкой" - да. "Круг является точкой" - нет, хотя у круга, как и у точки, есть координаты. Общие поля - ещё не повод наследоваться.

> Отсюда же одна странность Python: `isinstance(True, int)` возвращает `True`. Тип `bool` унаследован от `int`: логическое значение *является* числом, поэтому `True + True == 2`.

## Наследник дополняет и переопределяет

Наследник может:

- добавлять новые атрибуты и методы - как радиус и площадь у круга;
- **переопределять** методы родителя: метод с тем же именем заменяет родительский;
- переопределив метод, вызвать и родительскую версию через `super()`.

```python
class Shape:
    ...

    def describe(self):
        return f"фигура в точке ({self.x}, {self.y})"


class Circle(Shape):
    ...

    def describe(self):
        return f"круг радиуса {self.r}, " + super().describe()
```

```python
Circle(0, 0, 1).describe()      # 'круг радиуса 1, фигура в точке (0, 0)'
Rectangle(0, 0, 2, 3).describe()  # 'фигура в точке (0, 0)'
```

`Circle` переопределил `describe`, но не выбросил родительскую версию, а дописал к ней своё. `Rectangle` ничего не переопределял и получил метод `Shape` как есть.

Наследование может идти в несколько уровней. Квадрат - это прямоугольник с равными сторонами:

```python
class Square(Rectangle):
    def __init__(self, x, y, side):
        super().__init__(x, y, side, side)
```

```python
sq = Square(0, 0, 3)
sq.area()                    # 9
isinstance(sq, Rectangle)    # True
isinstance(sq, Shape)        # True
```

### 📝 Задача 4. Вклад и овердрафт

> **Файл:** `bank.py` | **Классы:** `Account`, `SavingsAccount`, `CheckingAccount`
>
> Скопируйте в этот файл `Account` из задачи 1 и сделайте `balance` свойством только для чтения, как в части 3.

В банке бывают счета разного назначения, и у каждого свои правила.

- **Сберегательный счёт** (вклад) копит деньги: банк начисляет на остаток проценты. При ставке 10% со счёта в 1000 рублей после начисления станет 1100.
- **Расчётный счёт** нужен для повседневных платежей, и к нему банк может подключить **овердрафт** - разрешение тратить больше, чем лежит на счёте, уходя в минус до заранее оговорённого лимита. Минус на счёте - это долг перед банком. Например, при остатке 100 рублей и лимите овердрафта 500 можно снять 600 рублей, и на счёте станет -500. Снять ещё хотя бы рубль уже нельзя, а следующее пополнение сначала гасит долг: после взноса 1000 рублей остаток будет 500.

Оба счёта умеют всё, что умеет обычный, поэтому их естественно сделать наследниками `Account`.

- `SavingsAccount(number, owner, balance=0, rate=0.05)` - сберегательный счёт, наследник `Account`.
    - Атрибут `rate` - процентная ставка.
    - `add_interest()` - начислить проценты: остаток увеличивается на `balance * rate`.
    - `__repr__` возвращает `SavingsAccount('1', 'Иван', 1100.0, 0.1)`.
- `CheckingAccount(number, owner, balance=0, overdraft=0)` - расчётный счёт с овердрафтом, наследник `Account`.
    - `withdraw(amount)` переопределён: можно уходить в минус, но не глубже `-overdraft`. Если после снятия остаток окажется меньше `-overdraft`, поднимите `ValueError` и не меняйте остаток. Сумма по-прежнему должна быть положительной.
    - `__repr__` возвращает `CheckingAccount('2', 'Мария', 700, 500)`.
- Оба наследника вызывают конструктор родителя через `super().__init__`, а `deposit` наследуют без изменений.

```python
s = SavingsAccount("1", "Иван", 1000, rate=0.1)
s.add_interest()
s.balance             # 1100.0
s.withdraw(2000)      # ValueError - как у обычного счёта
s.balance = 0         # AttributeError

c = CheckingAccount("2", "Мария", 100, overdraft=500)
c.withdraw(400)
c.balance             # -300
c.withdraw(300)       # ValueError: превышен овердрафт
c.deposit(1000)
c.balance             # 700
isinstance(c, Account)   # True
```

> **Проверьте себя:** получится ли написать `CheckingAccount.withdraw` через `super().withdraw(amount)`? Что пришлось бы поменять в `Account`, чтобы наследнику пригодилась родительская проверка суммы, но не проверка остатка?

# Часть 6. Полиморфизм и абстрактные классы

Вернёмся к смете и оформим её функцией:

```python
def total_area(shapes):
    total = 0
    for shape in shapes:
        total += shape.area()
    return total
```

Добавим в программу треугольник, заданный тремя сторонами. Площадь посчитаем по формуле Герона:

```python
class Triangle(Shape):
    def __init__(self, x, y, a, b, c):
        super().__init__(x, y)
        self.a = a
        self.b = b
        self.c = c

    def area(self):
        p = (self.a + self.b + self.c) / 2
        return math.sqrt(p * (p - self.a) * (p - self.b) * (p - self.c))

    def perimeter(self):
        return self.a + self.b + self.c
```

```python
plan = [Circle(0, 0, 1), Rectangle(10, 0, 4, 2), Triangle(0, 5, 3, 4, 5)]
round(total_area(plan), 2)   # 17.14
```

В программе появился новый вид фигуры, а в `total_area` и в любом другом коде, который работает с "фигурами вообще", не изменилось ни строчки. Сравните со словарями из части 1, где треугольник требовал правки каждой функции.

Это и есть **полиморфизм**: один и тот же вызов `shape.area()` выполняет разный код в зависимости от того, какой объект на самом деле лежит в переменной. Какой именно метод вызвать, решается во время выполнения программы, а не при её написании. В C++ для этого метод нужно пометить словом `virtual`, а в Python так ведут себя все методы. Главная польза полиморфизма: **код, написанный сегодня, работает с классами, которые появятся завтра**.

## Метод родителя вызывает метод наследника

Добавим в `Shape` метод отчёта:

```python
class Shape:
    ...

    def report(self):
        return f"площадь {self.area():.2f}, периметр {self.perimeter():.2f}"
```

```python
Triangle(0, 0, 3, 4, 5).report()   # 'площадь 6.00, периметр 12.00'
```

`report` написан в `Shape` и ничего не знает о треугольниках. Но `self` внутри него - конкретный треугольник, и `self.area()` находит метод треугольника. Вызов "проваливается" до самого конкретного класса, даже если он сделан изнутри родительского метода.

Так устроены игровые движки первой и третьей лабораторных. Движок написан заранее и в нужный момент вызывает у игрока метод выбора хода, а выполняется код вашего бота, о котором движок ничего не знал.

## Абстрактный класс

Что будет, если создать "просто фигуру" и попросить отчёт?

```python
Shape(0, 0).report()   # AttributeError: у Shape нет метода area
```

Фигуры "вообще" не бывает: у неё нет формулы площади. Хорошо бы запретить создавать такие объекты, а заодно гарантировать, что каждый наследник реализует `area` и `perimeter`. Для этого есть **абстрактные классы** и модуль `abc` (abstract base classes):

```python
from abc import ABC, abstractmethod


class Shape(ABC):
    def __init__(self, x, y):
        self.x = x
        self.y = y

    @abstractmethod
    def area(self):
        pass

    @abstractmethod
    def perimeter(self):
        pass

    def move(self, dx, dy):
        self.x += dx
        self.y += dy
```

```python
Shape(0, 0)   # TypeError: нельзя создать объект абстрактного класса
```

У эллипса нет простой формулы периметра, и автор класса про периметр "забыл":

```python
class Ellipse(Shape):
    def __init__(self, x, y, a, b):
        super().__init__(x, y)
        self.a = a
        self.b = b

    def area(self):
        return math.pi * self.a * self.b
```

```python
Ellipse(0, 0, 3, 2)   # TypeError: perimeter так и не реализован
```

- Класс, унаследованный от `ABC`, в котором есть хотя бы один метод с `@abstractmethod`, - **абстрактный**: создать его объект нельзя.
- Наследник, реализовавший *все* абстрактные методы, становится обычным классом. Забыл хотя бы один - остаётся абстрактным, и ошибка всплывёт сразу при создании объекта, а не через неделю при вызове `perimeter`.

Абстрактный класс, в котором *только* абстрактные методы, называют **интерфейсом**: сам он ничего не делает, а лишь описывает, что должны уметь наследники. Базовый класс `Player` в первой лабораторной - именно интерфейс: "бот умеет выбрать ход", а как - решаете вы.

## Утиная типизация

> Если что-то ходит как утка и крякает как утка, это утка.

В части 2 цикл по смете работал задолго до появления `Shape`: у кругов и прямоугольников просто были методы `area`. Python не проверяет тип объекта перед вызовом метода, он просто вызывает метод, и если метод есть, всё работает. Это называют **утиной типизацией**: важно не происхождение объекта, а то, что он умеет.

Зачем тогда абстрактные классы? Они превращают неявную договорённость "у фигуры есть `area`" в явную и проверяемую. Забытый метод обнаружится при создании объекта, а читатель кода сразу видит, что именно должен уметь наследник.

### 📝 Задача 5. Зоопарк

- `Animal(name, weight)` - **абстрактный** класс с атрибутами `name` и `weight` (вес в килограммах).
    - Абстрактные методы: `sound()` возвращает звук животного, `food_per_day()` - сколько килограммов корма ему нужно в день.

# Часть 7. Наследование или композиция

Соберём отношения между классами, от самого сильного к самому слабому.

| Отношение | Как звучит | Пример |
| - | - | - |
| наследование | A *является* B | круг является фигурой |
| композиция | A *состоит из* B и владеет им | дом состоит из комнат |
| агрегация | A *содержит* B, но не владеет им | группа содержит студентов |
| ассоциация | A *знает* о B | преподаватель знает студентов, которым ставит оценки |
| зависимость | A *пользуется* B | функция `total_area` пользуется фигурами |

На схемах классов эти отношения рисуют разными линиями. Такие схемы встречаются в документации и учебниках, и ими удобно набросать устройство программы до того, как писать код - например, архитектуру бота для лабораторной.

![Пять отношений между классами и как их рисуют на схемах](images/relations.svg#only-light)
![Пять отношений между классами и как их рисуют на схемах](images/relations.dark.svg#only-dark)

Ассоциация слабее агрегации: преподаватель не *состоит* из студентов и даже не содержит их, он лишь знает, кому ставить оценки. Зависимость - самая слабая связь: функция `total_area` не хранит фигуры, а только пользуется ими во время вызова. Но если у фигур переименовать метод `area`, функция сломается - в этом и состоит зависимость.

## Отрезок - это точка?

Самый частый вопрос проектирования - наследоваться или хранить объект в атрибуте. Вот пример: отрезку нужны координаты начала и конца. У точки координаты уже есть, так почему бы не унаследовать отрезок от точки и не дописать конец?

```python
class Segment(Point):
    def __init__(self, x1, y1, x2, y2):
        super().__init__(x1, y1)      # начало отрезка - это "я сам"
        self.end = Point(x2, y2)
```

Работает. Но наследник получил от точки *всё*, в том числе то, что для отрезка бессмысленно:

```python
s = Segment(0, 0, 3, 4)
s.move(1, 1)
((s.x, s.y), s.end)          # ((1, 1), Point(3, 4)) - сдвинулось только начало
isinstance(s, Point)         # True - отрезок можно передать туда, где ждут точку
round(s.distance_to(Point(0, 0)), 2)   # 1.41 - расстояние от отрезка? от начала?
```

`move` достался от точки и двигает только начало: отрезок молча деформировался. `distance_to` меряет расстояние от начала, хотя по имени кажется, что от отрезка. А раз `isinstance(s, Point)`, отрезок можно передать в любую функцию, которая ждёт точку, и получить чепуху без единой ошибки. Наследование утверждает "отрезок является точкой" - и это неправда.

Композиция решает задачу честно:

```python
class Segment:
    def __init__(self, x1, y1, x2, y2):
        self.start = Point(x1, y1)
        self.end = Point(x2, y2)

    def move(self, dx, dy):
        self.start.move(dx, dy)
        self.end.move(dx, dy)

    def length(self):
        return self.start.distance_to(self.end)
```

```python
s = Segment(0, 0, 3, 4)
s.move(1, 1)
(s.start, s.end)        # (Point(1, 1), Point(4, 5))
s.length()              # 5.0
isinstance(s, Point)    # False
```

Теперь отрезок *состоит из* двух точек и сам решает, что значит его сдвинуть. Наружу видно только то, что имеет смысл для отрезка.

![Отрезок через наследование и через композицию](images/inherit-vs-compose.svg#only-light)
![Отрезок через наследование и через композицию](images/inherit-vs-compose.dark.svg#only-dark)

Тот же вопрос возникает с кругом. У круга есть центр, но круг - не точка. Если унаследовать `Circle` от `Point`, у круга появится `distance_to`, которое меряет расстояние от центра, а не от окружности, а сам круг можно будет передать вместо вершины многоугольника.

Правило: **наследуйтесь, только если "является" - правда. Во всех остальных случаях выбирайте композицию.** Наследование связывает классы намертво: наследник получает всё, что есть в родителе, - и сейчас, и то, что туда добавят потом. Композиция берёт ровно то, что нужно.

# Для любопытных: функциональный стиль

Эпиграф занятия - слова Алана Кэя, который придумал сам термин "объектно-ориентированный". Для Кэя главным в ООП были не классы и наследование, а объекты, которые прячут своё состояние и обмениваются сообщениями. Ещё одной его идеей были **общие шаблоны поведения**, которые работают с данными любого типа. Такие шаблоны ярче всего видны в **функциональном программировании** - стиле, где программа собирается из небольших функций, а не из объектов, меняющих своё состояние. Python позволяет писать и так, и эти два стиля отлично дополняют друг друга.

Возьмём фигуры из частей 5 и 6:

```python
plan = [Circle(0, 0, 1), Rectangle(10, 0, 4, 2), Triangle(0, 5, 3, 4, 5)]
```

## Функция - тоже значение

Функцию можно положить в переменную, передать в другую функцию и вернуть из функции, как число или строку. Вы уже это делали: в `sorted(words, key=len)` функция `len` передаётся аргументом.

```python
def area(shape):
    return shape.area()

measure = area                 # функция в переменной, без скобок - не вызов
round(measure(Circle(0, 0, 1)), 2)   # 3.14
```

## `map`: применить функцию к каждому

`map(f, items)` применяет функцию `f` к каждому элементу и выдаёт результаты по одному; `list` собирает их в список:

```python
[round(a, 2) for a in map(area, plan)]   # [3.14, 8, 6.0]
list(map(len, ["круг", "квадрат"]))      # [4, 7]
```

Обратите внимание: `map` ничего не знает ни о фигурах, ни о строках. Ему всё равно, что лежит в списке и что возвращает функция, - он лишь применяет одно к другому. В чисто функциональном языке Haskell эта идея записывается одной строкой - типом функции `fmap`:

```haskell
fmap :: (a -> b) -> f a -> f b
```

Читается так: "дай мне функцию, которая превращает `a` в `b`, и контейнер со значениями `a` - получишь контейнер со значениями `b`". Здесь `a` и `b` - любые типы, а `f` - любой контейнер, который умеет так себя вести. Это и есть универсальный шаблон поведения, о котором говорил Кэй: в первом примере `a` - фигуры, `b` - числа; во втором `a` - строки, `b` - тоже числа, а код `map` один и тот же.

## `filter` и `sorted`: отбор и порядок по функции

```python
big = list(filter(lambda s: s.area() > 5, plan))
[type(s).__name__ for s in big]                     # ['Rectangle', 'Triangle']
[type(s).__name__ for s in sorted(plan, key=area)]  # ['Circle', 'Triangle', 'Rectangle']
```

`filter` оставляет элементы, для которых функция вернула `True`, а `sorted` расставляет их по значению функции-ключа. `type(s).__name__` - имя класса объекта.

## Функция, которая создаёт функции

Условие "площадь больше 5" зашито в `lambda`. Чтобы не писать новую `lambda` для каждого порога, сделаем функцию, которая *возвращает* проверку под нужный порог:

```python
def larger_than(limit):
    def check(shape):
        return shape.area() > limit
    return check

big_enough = larger_than(5)
big_enough(Circle(0, 0, 1))                 # False
len(list(filter(larger_than(3), plan)))     # 3
```

Внутренняя функция `check` запоминает `limit`, с которым её создали. Такую функцию называют **замыканием**.

## Не менять, а создавать новое

Функциональный стиль предпочитает не менять объекты, а возвращать новые. Вспомните часть 4: `move` меняет точку на месте, и все ярлыки, привязанные к ней, видят изменение - иногда это сюрприз. Функция, которая возвращает *новую* точку, таких сюрпризов не устраивает:

```python
def moved(point, dx, dy):
    return Point(point.x + dx, point.y + dy)   # новая точка, старая не тронута

path = [Point(0, 0), Point(3, 4), Point(6, 0)]
shifted = list(map(lambda p: moved(p, 1, 1), path))
shifted       # [Point(1, 1), Point(4, 5), Point(7, 1)]
path[0]       # Point(0, 0) - исходный путь цел
```

Функцию, которая ничего не меняет вокруг себя, а только возвращает результат, называют **чистой**. Её проще проверять: при одних и тех же аргументах она всегда даёт один и тот же ответ. Так уже устроены `__add__` у векторов и `+` у денег в балльных задачах.

## Свернуть всё в одно значение

Последний кирпичик - `reduce` из модуля `functools`. Он проходит по списку и накапливает результат: начинает со стартового значения и на каждом шаге комбинирует накопленное со следующим элементом. Вот вся смета одной строкой:

```python
from functools import reduce

round(reduce(lambda total, s: total + s.area(), plan, 0), 2)   # 17.14
```

`map`, `filter` и `reduce` - три базовых шаблона: преобразовать каждый элемент, отобрать нужные, свести всё к одному значению. Из них складывается удивительно много программ.

Заметьте, что функциональный код здесь опирается на объектный: `map(area, plan)` работает только потому, что каждая фигура сама знает свою площадь. Классы описывают, *что такое* данные и что они умеют; функции вроде `map` и `filter` описывают, *что с ними делать* целыми наборами. Хороший код на Python обычно пользуется и тем и другим.
